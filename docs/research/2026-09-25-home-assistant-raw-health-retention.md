# Retaining historical health points in Home Assistant

Research date: 2026-09-25. Scope: whether a future full-history HealthKit import can keep its detailed points indefinitely, alongside useful Home Assistant history and statistics. This is a design assessment, not a verified live installation.

## What Home Assistant retains

- Recorder stores individual entity state changes in its `states` table. Its automatic purge defaults to 10 days; `purge_keep_days` sets one recorder-wide interval, and `auto_purge: false` disables the automatic purge. Recorder warns that unbounded growth consumes disk, can slow Home Assistant, and may require temporary free space at least as large as the database for maintenance or migration. The documented `include`/`exclude` filters control which entities are recorded, not separate retention periods per entity. [Recorder configuration and disk guidance](https://www.home-assistant.io/integrations/recorder/).
- Long-term statistics are separate hourly aggregates, retained indefinitely by normal purging. For measurement sensors they contain mean, minimum, and maximum; they do not preserve each original point. The History panel switches to these aggregates beyond detailed recorder retention. [Home Assistant data model](https://data.home-assistant.io/docs/statistics/), [History data sources](https://www.home-assistant.io/integrations/history/).
- Therefore, retaining *all* detailed state rows within native Home Assistant History is technically possible by disabling automatic purge (and avoiding manual purges), but applies to the whole recorder database. It is a poor default for years of high-frequency health points. Setting a very long `purge_keep_days` has the same broad storage effect. Keeping a separate raw archive cannot by itself make old points appear in native History; that would require a custom view/query path or retaining the recorder rows. This last sentence is a design inference from Home Assistant's documented data sources. [Recorder](https://www.home-assistant.io/integrations/recorder/), [History](https://www.home-assistant.io/integrations/history/).

## The pinned Health Bridge v1.2.1 baseline is not durable historical storage

The pinned Health Bridge v1.2.1 backfill accepts numeric `timestamp`/`value` metric points, limits them to the most recent 14 days, inserts them only as recorder state history, and acknowledges `statistics_policy: "history_only"`. It does not write long-term statistics or a separate archive. Points older than the recorder retention threshold will be purged. [Pinned protocol implementation and limits](https://github.com/gregt1993/Health_Bridge/blob/3d227252e80cdd42827f026082230215197bd583/custom_components/health_bridge/history_backfill.py#L24-L40), [recorder insert](https://github.com/gregt1993/Health_Bridge/blob/3d227252e80cdd42827f026082230215197bd583/custom_components/health_bridge/history_backfill.py#L299-L417), [backfill acknowledgement](https://github.com/gregt1993/Health_Bridge/blob/3d227252e80cdd42827f026082230215197bd583/custom_components/health_bridge/history_backfill.py#L73-L99). The newer v2.1.0 release adds workout and sleep text backfill but retains these durability limits; see the [upstream refresh](2026-09-25-health-bridge-upstream-refresh.md).

These are *derived metric points*, not complete HealthKit samples: the iOS request serializes only `timestamp` and `value`, with no HealthKit sample UUID, source, end time, or metadata. Retaining the exact source samples would require an explicit new data contract and user-facing privacy/storage design. [App backfill request](../../Packages/HealthSyncCore/Sources/HealthSyncCore/HealthBridgeProtocol/BackfillRequest.swift), [pinned Health Bridge request parsing](https://github.com/gregt1993/Health_Bridge/blob/3d227252e80cdd42827f026082230215197bd583/custom_components/health_bridge/__init__.py#L184-L242).

## Recommended fork design for maximum usability

1. Keep normal recorder purging for the rest of Home Assistant. In the compatible Health Bridge fork, persist each supported historical metric point to an integration-owned durable archive (stable user/metric/source-point identity, timestamp, value, unit, and enough provenance for corrections and deletions). Add bounded, authenticated range queries and an export path. Treat this as the long-lived detailed copy.
2. Populate Home Assistant long-term statistics for the same eligible metrics so multi-year trends remain visible in native statistics/history views. Use Home Assistant's statistics import facilities and verify the meaning of `measurement` versus `total`/`total_increasing` for each metric; hourly aggregates cannot be reconstructed accurately by blindly summing or averaging every health type. [Statistics model](https://data.home-assistant.io/docs/statistics/), [sensor state classes](https://developers.home-assistant.io/docs/core/entity/sensor/), [core statistics import queue](https://github.com/home-assistant/core/blob/dev/homeassistant/components/recorder/core.py).
3. Use recorder state history only for a recent detailed window, if native History detail is desired. The durable archive needs its own view/API for old point-level exploration; Home Assistant's stock History panel reads recorder history and hourly statistics. [History data sources](https://www.home-assistant.io/integrations/history/).

This is a proposed architecture, not a feature of the existing integration. The archive needs backup/restore, migration, idempotency, capacity limits, and deletion/correction semantics. An external time-series store is also possible: Home Assistant's InfluxDB integration streams state changes to a separate database, but it runs in parallel with recorder and does not itself turn old Health Bridge backfill rows into durable historical samples. [InfluxDB integration](https://www.home-assistant.io/integrations/influxdb/).
